# 公网部署前安全检查报告

检查日期：2026-10-30（Asia/Shanghai）  
检查对象：ArcSync 0.3.0 当前仓库代码、Python 已安装依赖与仓库内部署模板。

**结论：当前版本适合作为受控本地演示，不建议直接对公网开放。默认管理口令、具名身份与数据隔离、登录和模型调用限流是上线阻塞项。** 本报告没有修改运行代码、用户口令、权限或业务数据库，也没有执行公网扫描或真实付费模型调用。

## 检查方式与边界

- 静态检查：入口与会话、岗位/业务权限、智能体工具及来源、模型配置、MySQL 连接、部署和文件打包。
- 动态复现：独立临时 SQLite、隔离会话、FastAPI ASGI 请求；模型诊断使用 HTTP 客户端替身，不访问真实模型、不产生调用费用。MySQL TLS 默认值通过当前已安装 PyMySQL 的连接对象（defer_connect，不连接服务器）及驱动实现核实。
- 功能基线：本轮既有48项自动测试通过，不能替代公网安全验收。
- 依赖检查：独立临时环境运行 pip-audit，查询本机项目环境中26个已安装分发包，结果为 **0条已知漏洞、0个跳过包**。这只代表当日所查询漏洞数据库结果，不代表代码没有漏洞；也不能替代未来 Linux/容器生产环境的重新扫描。
- 没有云主机、域名、反向代理、数据库和模型服务部署配置的实际运行证据，不能判定这些外部环境已经安全。真实 MySQL、真实 LLM 对抗测试、外部端口、证书、云安全组和操作系统补丁未验证。

复现原始结果：[隔离检查证据](security/evidence-2026-10-30.json)；依赖原始结果：[依赖扫描 JSON](security/dependency-audit-2026-10-30.json)。

## 按上线优先级排列的问题

### SEC-01 / 严重：默认演示口令能直接登录管理岗位

**位置：** `src/arcsync/core/store.py:81–84`；`src/frontend/app.js` 的 renderLogin/account 处理；`src/arcsync/api/security.py:33–46`。

首次初始化默认创建六个岗位账号，同一演示口令在欢迎页/前端脚本明确展示并可自动填入。隔离库中 director、protector、engineer 使用默认演示口令均返回200。任何能访问公网登录页的人都能按此初始化默认值尝试获得管理权限；这不是绕过鉴权，而是有效管理凭据被公开。

另已复现：改变 ARCSYNC_DEMO_PASSWORD 并再次初始化后，旧密码仍可登录，因为 INSERT OR IGNORE 不更新已有用户。**仅修改环境变量不足以修复已有数据库。** 本次没有检查或尝试登录用户实际工作库中的默认口令，不能据此声称实际账号目前仍使用该密码。

**整改：** 生产模式禁用演示账号生成、口令展示和自动填入；启用具名账号或组织 SSO，管理岗位启用 MFA；使用受控初始化流程设置管理员并强制首次改密。对已有库显式轮换凭据并撤销旧会话，生产启动时拒绝已知默认口令。不要只从前端删提示。

### SEC-02 / 高：身份与权限只做到岗位，没有人员、部门和业务关系隔离

**位置：** `core/store.py:55`、`core/service.py:49–51,80–94`、`agents/repository.py:24–35`、`agents/tools.py:60–70`。

users 的主键就是 role，业务 owner 和运行历史也按 role 归属。两个浏览器以 organizer 登录，后一会话可以读取前一会话的智能体运行记录；系统没有独立人员身份，日志也不能区分同岗位的不同员工。

`GET /api/state` 对所有已登录岗位返回全量 businesses、handoffs、feedback 和最近500条 events。隔离测试中，查询代表能够取得审核岗业务的测试随单备注。智能体的 get_business_status 也仅按业务编号读取，没有对象级授权。

如果组织明确允许所有员工读取全部业务，则该读取行为属于当前策略；**但当前代码无法满足“只能看本人/部门/经授权业务”的公网多用户要求**。前端隐藏菜单和业务写操作的责任岗位校验不能替代读取权限。

**整改：** 引入独立 user_id、角色映射及部门/租户/业务成员关系；业务和 agent_run 保存创建人/责任人；统一对象级授权覆盖 state、详情、事件、反馈、交接、工具和导出。历史与缓存读取也需套用同一规则；补充跨员工、跨部门、跨租户的读写拒绝测试。

### SEC-03 / 高：登录缺少节流、风险阻断和失败审计

**位置：** `api/security.py:33–46`、`api/routes.py:45–50`。

隔离测试连续12次错误登录均返回401，没有429、递增等待或锁定，随后正确登录直接成功。代码无账号/IP失败计数，失败尝试也未追加审计。攻击者可持续猜测密码，并占用密码哈希线程池和数据库连接。固定长度会话虽有8小时过期，但没有禁用账号、全量撤销会话及管理操作二次认证流程。

**整改：** 网关和应用双层限流；以账号为主结合可信客户端来源计数，渐进延迟和临时阻断，避免只按IP锁定正常用户；失败事件、异常登录和管理操作告警。生产身份体系提供账号停用与会话撤销，调整密码哈希强度或采用当前推荐方案。

### SEC-04 / 高：模型诊断接口可绕过智能体并发控制，缺少费用与资源配额

**位置：** `api/agent_routes.py:21,27–40,54–77`、`data_models/vectors.py:73–87`、`data_models/providers.py:13–16`。

`/api/agent/chat/stream` 有单进程4个任务及每岗位1个任务限制，**不是完全没有并发控制**。但 `/api/admin/models/check` 每次实际调用一次对话与一次嵌入，不经过该限制，也没有冷却时间、每日额度或预算。把 engineer 标记为已有运行后，6个并发诊断请求仍全部200，替身计数为6次chat和6次embed。

`_active` 只在当前进程内有效，多 worker/多实例会各算一份。连续提交、冷索引嵌入、无分页业务读取及不断增长的向量快照/审计记录还会消耗计算、磁盘和数据库资源。90秒是上游读超时，不是整个任务的绝对执行期限；持续收到数据的上游可能延长运行。

**整改：** 对所有付费模型入口统一共享的用户级/全局并发、频率、token/嵌入量与费用预算；诊断单独冷却；设置整体任务截止时间和队列长度。索引构建后台化并去重，规划文件/记录配额与清理；提供账单阈值、熔断及告警。单进程集合不能当多实例配额。

### SEC-05 / 高（远程数据库部署时）：MySQL 不强制证书/主机名校验，允许 TLS 降级

**位置：** `data_models/mysql.py:24–31`。

业务连接未传入 ssl_ca、ssl_verify_cert、ssl_verify_identity 等参数。当前 PyMySQL 1.2.3 在默认配置下会优先尝试 TLS，但允许在服务不支持时回退；隔离构造结果为 `_ssl_required=False`、证书校验关闭、主机名校验关闭。

因此**不能声称现在所有 MySQL 连接均明文**；问题是代码没有强制加密和验证对端身份。远程 MySQL 链路存在窃听、降级与冒充数据库的风险。同机回环地址或受控本地容器链路的风险不同，实际生产服务端是否强制 TLS 尚未检查。

**整改：** 增加生产数据库 TLS 配置，强制证书链和主机名验证；连接失败时不降级。数据库在私网，生产运行账号和建表/迁移账号分开，应用账号限制为必要读写权限。数据库侧同步要求安全传输。

### SEC-06 / 上线必验：仓库还没有完成公网 HTTPS 和网关部署防护

**位置：** `main.py:43–49,75–82`、`api/routes.py:45–49`、`scripts/deploy.sh`。

当前入口只监听127.0.0.1，deploy.sh 只是本地运行说明；这本身减少暴露，不是已经完成线上部署。仓库未提供可验证的 HTTPS 终止、域名白名单、HSTS、可信代理、连接/请求限流及访问告警配置。

已复现 HTTP 登录的 Cookie 有 HttpOnly/SameSite=Strict，但没有 Secure；HTTPS 模拟请求会正确设置 Secure。若反向代理没有正确传递/校验协议，Cookie 属性与 POST Origin 校验可能不符合外部 HTTPS 地址。任意 Host 请求当前可返回页面，域名限制应由应用或网关落实。

**上线要求：** HTTPS统一入口，确认安全Cookie及可信转发头；限制合法域名；应用、MySQL、Ollama/vLLM 只在私网/回环可达，公网只开放必要的网关端口。配置进程管理、最小权限运行用户、请求体/连接超时、速率/并发与日志。不要仅把 Uvicorn 改为0.0.0.0便视为可安全上线。

## 中等风险与后续事项

- **LLM 内容与知识污染：** 来源编号正则、当前权限/版本校验不等于判断结论被原文支持。工程师/保护专员导入的正文或用户问题可能包含提示注入，影响模型回答。当前工具只有受控只读能力，尚未发现模型直接执行 SQL、Shell、审批或解密的接口；不能把这一剩余风险表述为已证实的远程代码执行。上线仍需真实模型对抗样本、知识发布审核、异常答案处置和人工复核。
- **数据静态保护和留存：** 问题、来源全文、模型回答、向量、会话 token 均在应用数据存储中，未实现应用层加密/独立密钥管理、自动留存清理和生产备份恢复验证。会话 token 为数据库明文值，读库者可能直接复用未过期会话；生产可改为保存 token 哈希。用磁盘/备份加密和最小权限保护数据，按组织规则定义留存与恢复演练。
- **审计独立性：** 审计触发器可挡普通 UPDATE/DELETE，但拥有改表/触发器权限的数据库账号仍可破坏它。运行账号因启动建表而需要较大权限；需拆分迁移身份并将关键日志送到独立、受控留存的日志系统。
- **暴露面与依赖：** OpenAPI和文档公开不是登录绕过，但正式部署可以关闭或限制它们。当前直接依赖固定版本，间接依赖没有完整锁定/哈希，部署时应生成可复现的锁文件并持续扫描；本机扫描结果不能外推到未来镜像。

## 已存在的有效保护

- 随机服务端会话、密码加盐哈希、常量时间比对、登录会话轮换、退出删除与过期检查。
- HttpOnly、SameSite=Strict，HTTPS请求下的Secure；POST自定义头、JSON限制和Origin校验；CSP、nosniff、禁止嵌框与静态文件白名单。
- 普通员工读取后台overview返回403，直接读取受限档案返回404。`/.env`、数据库、向量路径、需求源文件的静态HTTP读取均返回404。
- SQL参数绑定、源文件和运行数据库不打包、密钥不回传浏览器、工具白名单与调用/轮次上限、授权候选集先过滤再FAISS检索。
- 源文/版本变化会阻断旧回答或交付；旧页文本保留；人工确认与交付仍走既有规则。

这些保护应保留，不能把“存在高风险”理解为所有安全措施均缺失。

## 上线整改顺序与通过条件

1. **先处理身份与权限：** 禁用默认演示凭据，轮换现有口令和会话；具名身份、管理MFA；明确员工/部门/租户和业务关系并在接口/工具统一实施。
2. **再处理滥用与链路：** 登录和模型接口共享限流、费用配额与审计告警；HTTPS、可信代理、Secure Cookie、域名限制；远程MySQL强制验证TLS，模型与数据库不对公网开放。
3. **最后做运行验收：** 真实部署环境重新扫描依赖与端口，完成跨账号授权、暴力尝试、额度耗尽、反向代理协议、证书失败拒绝连接、备份恢复和真实模型提示注入测试。

SEC-01/02/03/04不得保留后直接公网开放。SEC-05在使用远程数据库时必须解决，SEC-06须用实际网关配置与测试证据确认。修复后重新审查，本轮检查不是安全上线批准或完整第三方渗透测试。

## 复查方法

在项目根目录运行：

```sh
.venv/bin/python docs/security/reproduce_checks.py
```

脚本仅使用临时SQLite及模拟模型，不改实际业务库，不访问真实模型；它输出“当前是否仍存在这些行为”的证据，而不是安全通过证书。输出文件写入系统临时目录。部分复现依赖当前接口，修复身份模型后应相应调整检查脚本。
