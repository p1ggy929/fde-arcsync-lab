# 设计说明

## 定位与范围

本地合成数据演示，按 discovery-report 的 REQ-1 至 REQ-6 建立可操作流程。资料版本、引用核对、接手确认和异常处理优先于智能生成。

## 架构

浏览器原生 HTML/CSS/JavaScript → 同源 JSON API → Python 业务服务 → SQLite。

首期采用无第三方依赖的模块化单体，便于离线启动与交付。前端不是权限边界；业务条件、岗位、责任、状态、资料版本和页码均在后端校验。

`main.py` 负责 HTTP、会话、请求限制与合成卷页读取，`core/service.py` 负责确定性业务操作，`core/store.py` 负责数据初始化与审计存储。`integrations/base.py` 仅为后续真实数据源定义契约。

## 业务实体

- documents：档号、版本、类别、年度、公开级别、资料状态、更正关系、页码映射。
- businesses：业务号、申请信息、状态、当前责任岗位、草稿、引用、记录修订号、预置样例标记。
- citations：在业务中保存档号、资料版本、扫描页、纸质页、人工确认者与时间。
- handoffs：交出岗位、接手岗位、未解决事项、发送时间、接手确认时间。
- issues：触发原因、关联档案、分派岗位、状态、处理结果。
- events：按业务记录创建、核验、引用确认、审核、退回、交接与交付时间。
- feedback：原业务、当时资料版本、诉求、审核核对结果。
- audit：操作人、岗位、时间、业务号与操作凭证，数据库触发器禁止应用更新和删除。
- users / sessions：演示账号口令哈希、服务端随机会话与过期时间。

## 状态与责任

正常状态：待权限核验 → 定位中 → 待审核 → 待交付 → 已交付。

异常路径：处理中 → 异常处理中 → 分派与处理 → 待复核 → 恢复定位。

提交、权限核验、退回与异常复核等跨岗动作创建待接手交接。接手之前不修改当前责任岗位，目标岗位必须确认接手。交接待确认期间阻止正常业务推进。发生新异常时取消旧的待接手交接，保留交接记录和异常原因。

并发修改由事务内记录版本检查保护。HTTP 写操作使用 SQLite `BEGIN IMMEDIATE` 串行化写入，陈旧 revision 返回 409，不覆盖后保存内容。

处理状态以岗位为责任单位，因为每个岗位在演示中仅一个账号；生产多人员岗位需改为具名用户、组织与委派关系。

## 资料与引用校验

资料必须有效、已授权、版本一致、扫描页在范围内且纸质页符合映射。存在后续更正必须人工确认已核对。资料更正关系完整性在真实接入后才可验证，当前仅展示固定关系。

已更正和待修复资料可在授权范围查看，但不能加入引用。人工修复结果保存为独立记录，不自动覆盖源档案或解除质量标记。审核时再次核对引用所用资料版本。

## 同步与故障

合成数据快照显示时间戳，超过一小时标为待刷新。工程师刷新仅更新时间戳，不请求外部系统。接口接入、权限撤销传播、快照保留期限、断线补齐幂等性和重连触发条件尚待实现及确认。

网页无法连接本地服务时提示失败，不把未保存草稿标为已同步；草稿只有服务端写入成功后显示保存成功。当前未提供浏览器离线缓存或离线写入，避免在浏览器长期保存档案内容。

## 评估边界

预置样例不计入新建业务计数，新建业务本身也仍为演示。未有金标准样本、完整流程时间口径及独立人工判定，准确率、泄露、定位提速显示为待验证。事件记录支持后续复算，不把通知发送量当完成量。
